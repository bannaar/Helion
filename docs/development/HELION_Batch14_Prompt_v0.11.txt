============================================================
40A. LIGHTWEIGHT BINARY PROTOCOL MODERNIZATION
============================================================

The current native protocol is a bounded newline/text command protocol over TLS, not JSON. Preserve TLS 1.2+ and server authority, but introduce a binary protocol foundation where it provides measurable value.

The goal is lower bandwidth, lower parse/format overhead, clearer schemas, and safer high-frequency replication as HELION grows.

Do NOT send raw C/C++ object memory over the network.
Do NOT rely on #pragma pack, compiler padding, host endianness, enum size, bool layout, pointer layout, or memcpy of native structs as the wire contract.

Preferred architecture:
- TLS remains the encrypted transport
- binary framing exists above the TLS byte stream
- fixed-width integer types are used on the wire
- byte order is explicit and consistent
- floating-point fields are serialized explicitly if used
- every frame has a bounded payload length
- message types are explicit/stable IDs
- protocol/schema version is explicit
- request/correlation IDs exist where useful
- incremental decoding handles partial and multiple frames
- oversized, malformed, unknown, and incompatible frames fail safely
- no unbounded allocation is permitted from untrusted length fields

A compact frame header may contain fields equivalent to:
MAGIC / PROTOCOL_VERSION / MESSAGE_TYPE / FLAGS / PAYLOAD_LENGTH / REQUEST_ID

Use repository conventions and the smallest safe representation.

Serialization choice:
- FlatBuffers is acceptable if repository inspection shows its generated-schema/runtime/build cost is justified and remains lightweight on the target hardware.
- A small explicit custom encoder/decoder is also acceptable for HELION's current message set.
- Raw ABI-dependent packed structs are NOT acceptable as the durable cross-version wire format.

Prioritize high-frequency/state-heavy messages first, such as where implemented:
- INPUT / player control
- authoritative flight snapshots
- contacts/entity replication
- combat state/deltas
- market/ship/outfitting snapshots or deltas when their volume warrants it

Low-frequency human-readable diagnostics may remain available through a developer terminal UI, but the terminal should preferably translate human commands into the same typed protocol operations rather than require a separate insecure production command grammar.

Do not maintain two uncontrolled gameplay authorities.

Compatibility/migration:
- negotiate or verify protocol version before normal gameplay
- reject incompatible versions deterministically
- preserve a clear CLIENT_UPDATE_REQUIRED / incompatible-protocol path
- TEST and PRODUCTION may advertise different approved protocol/build versions
- legacy text protocol support, if temporarily retained, must be explicit, bounded, tested, and removable; do not silently auto-detect arbitrary byte streams forever

Measurement requirement:
Benchmark representative old text framing versus the new binary path on realistic message samples. Report:
- encoded bytes per message
- aggregate bytes for a representative gameplay interval
- encode time
- decode time
- allocation behavior where practical

Do not claim a bandwidth/CPU win without measurements. If the measured benefit is negligible for a low-frequency message, keep the simpler implementation.

Security tests must cover:
- truncated headers
- partial frames
- multiple frames per read
- oversized declared payloads
- invalid message IDs
- invalid protocol versions
- malformed field values
- replay-sensitive transactional messages where applicable
- fuzz-like random byte input to the bounded decoder where practical

through the state controller without duplicating gameplay rules.
